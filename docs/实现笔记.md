## 一、坐标系与几何（最深的坑）

### 1.1 SUN RGB-D 的 GT 框不在相机系里

**现象**
把 GT 3D 框的中心用相机内外参投影到图像，结果**全部落在画面外或相机后方**
（`z` 全为负），有效投影率 **0%**。

**排查过程**（这就是为什么留了两个标定脚本）
枚举了 7 种坐标系假设，用两个判据打分：
1. 框中心投影是否落在画面内且 `z > 0`；
2. **角点闭环一致性** —— GT 角点 → 投影 → 读深度 → 反投影 → 与 GT 角点比距离。

结果：

| 假设 | 中心投影有效率 | 角点闭环误差中位数 |
|---|---|---|
| 框在相机系（R=I） | 0.00 | — |
| `R = Rtiltᵀ` | 0.00 | — |
| **`R = Pᵀ`（固定轴置换）** | 0.89 | 1.66 m |
| **`R = Pᵀ @ Rtiltᵀ`** | 0.68 | 0.86 m |
| `R = Rtiltᵀ @ Pᵀ` | 0.65 | **0.78 m** |
| `R = Rtilt @ Pᵀ`（顺序反了） | 0.38 | 2.21 m |

**根因**
SUN RGB-D 的 GT 框位于**标注工具用的重力对齐世界系**（x 右、y 深度、z 上），
而 `Rtilt` 本身接近单位阵（实测约 12° 小倾斜），是**传感器残余倾斜的精修**，
作用在**相机原生轴**上。所以顺序必须是"先 Rtilt，再做轴置换"。

**解法**
```python
CameraPose.from_sunrgbd(Rtilt)   # R_wc = Rtiltᵀ @ Pᵀ
```

**注意顺序反了会怎样**：`Rtilt @ Pᵀ` 的闭环误差是 `Rtiltᵀ @ Pᵀ` 的 **2.8 倍**。
这不是"随便选一个差不多"，是有 2.8 倍差距的。

**证据**：`scripts/calibrate_sunrgbd_geometry.py`、`scripts/diagnose_sunrgbd_frame.py`
（可随时重跑复现这张表）。

### 1.2 `coeffs` 是全边长，不是半边长

**现象**：训练/评测时 3D 框看起来"大得离谱"，床有 4 米宽。

**根因**：SUN RGB-D 的 `groundtruth3DBB.coeffs` 文档表述模糊。
用物理常识一验就清楚了：

| 类别 | `coeffs` | 当全边长 | 当半边长 |
|---|---|---|---|
| bed | (1.89, 2.30, 1.97) | 1.9×2.3m 的床 ✔ | 3.8×4.6m 的床 ✘ |
| nightstand | (0.58, 0.55, 0.90) | 0.58m 床头柜 ✔ | 1.15×1.09×1.8m ✘ |

**解法**：`size = coeffs`（不要 `2 * coeffs`）。

**附带发现**：`G:\Embodied3D` 项目的预处理里写的是 `size = 2.0 * coeffs`，
也就是它的 3D 框被放大了整整一倍。这是一个可复现的真实 bug。

**方法论**：数据集文档不可信时，用**物理常识**当判据 —— 床不可能 4 米宽。

### 1.3 深度尺度是 /10000

**现象**：点云尺度差 10 倍（门只有 20cm 高）。

**根因**：SUN RGB-D 的 depth PNG 是 uint16，数值范围 1.2 万~4.5 万，
单位是 0.1mm，所以 `depth_m = raw / 10000`。很多教程写 `/1000`（那是别家的数据）。

**解法**：`geometry.depth_scale` 必须由配置显式给出，默认 1000，
SUN RGB-D 的配置里写 10000。

### 1.4 opencv 读 16 位 PNG 会静默返回 None

**现象**：深度图全是 0，点云是空的，但没有任何报错。

**根因**：`cv2.imread` 对 SUN RGB-D 的 16 位 depth PNG 返回 `None`
（opencv-python 5.x 的这个行为）。因为是"返回 None"而不是抛异常，
下游 `np.asarray(None)` 会得到一个奇怪的 0 维数组，错误被推迟到很远的地方才爆。

**解法**：读深度一律用 PIL，并**显式检查返回值**：
```python
raw = np.asarray(Image.open(depth_path))
if raw.ndim != 2: return None    # 早失败，别让错误飘到下游
```

### 1.5 `project_points_to_image` 的 NaN 陷阱

**现象**：单元测试发现**相机后方的点**投影出了一个"看起来合法"的像素坐标。

**根因**：
```python
uv = np.full((N, 2), np.nan)          # 初始化成 NaN
uv[:, 0] = cam[:, 0] * fx / safe_z + cx   # ← 向量化赋值把 NaN 覆盖了！
uv[:, 1] = cam[:, 1] * fy / safe_z + cy
```
用 `safe_z = np.where(front, z, 1.0)` 避免除零，但同时也让后方点算出了一个假坐标。
**初始化 NaN 完全没用，因为赋值是无条件的。**

**影响**：如果不修，stub 检测器会把相机后方的框也投影成检测框，
产生完全错误（镜像位置）的检测。

**解法**：显式重置
```python
uv[~front] = np.nan
```

**这就是为什么要写单元测试** —— 这个 bug 在真实数据上看不出来（大多数时候框在前面），
只有在边界条件下才暴露。

### 1.6 GPU 计时不 sync 会低估延迟

**现象**：同一个模型在 GPU 上测出来比 CPU 还快，明显不合理。

**根因**：CUDA 是异步的。不调用 `torch.cuda.synchronize()`，
`time.perf_counter()` 测到的是"内核提交完成"的时间，不是"算完"的时间。

**解法**：`eval/benchmark.py` 的 `_Stopwatch` 在每次计时前后都 sync。

## 二、地图构建

### 2.1 空间聚类会把相邻物体粘成一个

**现象**：地图里"杯子"和"桌子"变成了同一个物体，`describe()` 只显示一个标签。

**数据**：190 个体素 → **1 个物体**（应该是 2 个）。

**根因**：DBSCAN 用 `eps=0.08` 做邻域。桌子的右边界体素在 x=-0.27，
杯子的左边界在 x=-0.20，距离 0.07 < 0.08 → **被连成一簇**。

空间聚类只看"几何上挨不挨着"，而"挨着"在真实场景里太常见了
（桌上的杯子、椅边的包、靠墙的柜子）。

**解法**：改用**实例级关联**。

```
每个检测 = 一个实例（标签 + 3D 点集）
关联判据：标签语义兼容 AND (中心距离 ≤ 0.6m OR 3D IoU ≥ 0.1)
→ 命中已有轨迹则融合，否则新建轨迹
```

**效果**：3 个正确分离的物体，标签正确，不再合并。

**保留降级**：`object_mode: clustering` 仍可用（当只有体素网格没有实例信息时），
但 docstring 里明确写了它的局限。

### 2.2 查询返回了"零分命中"

**现象**：查询"电视"（地图里没有电视）也返回了一个物体，只是 `score=0.000`。

**根因**：`if score < min_score: continue`，而 `min_score` 默认是 `0.0`，
所以 `0.0 < 0.0` 为 False，零分候选被放行。

**影响**：调用方会误以为"查到了东西"。对机器人来说这是危险的 ——
它可能据此去一个完全错误的位置。

**解法（第一版）**：`query.min_score` 默认改成 `0.05`，并且验证
"电视/显示器"在地图只有 cup/table/chair 时返回空列表。

**教训**：**"没找到"必须是一个明确的、能被返回的状态**，
不能让低分候选冒充命中。

### 2.2b ★ 上面那个修法**只修对了一半**（0.05 仍然太低）

**现象**：2.2 修完之后所有测试都是绿的，看起来问题解决了。
但后来写开放词汇评测（`scripts/16_eval_openvocab_query.py`）时发现：
**72 条"地图里确定没有的类别"查询里，有 27.8% 依然返回了错误物体**。

**根因**：词法打分是**分层的**（`LexicalMatcher.score`）：

| 层级 | 规则 | 分数 |
|---|---|---|
| 1 | 规范概念命中 | 1.00 |
| 2 | 子串包含 | 0.85 |
| 3 | **字符 bigram Jaccard** | `min(0.8, sim×1.6)` |

第三层是**纯噪声源**：任意两个词只要共享少量 bigram 就有分。
实测 `bicycle` 与 `bottle` 共享 bigram `le`，
Jaccard = 1/11 = 0.09 → 得分 **0.145**，刚好越过 0.05 的阈值。
`helicopter`、`airplane`、`冰箱`、`宇宙飞船` 同理。

**解法（第二版）**：阈值抬到 **0.5** —— 高于第三层噪声、低于真信号（0.85/1.00）。

**效果**（6 场景 / 151 条未见表达 / 72 条未见类别，**纯词法路径**）：

| 阈值 | 命名类命中 | 描述类命中 | 拒识率 | 综合分 |
|---|---|---|---|---|
| 0.05 | 100.0% | 37.5% | 72.2% | 0.603 |
| **0.5** | **100.0%** | 35.0% | **100.0%** | **0.828** |

命名类命中率**一点没降**，拒识率从 72.2% 拉到 100%。
（hybrid 路径在 0.5/0.02 下是 0.834 —— 嵌入恰好救回被严格阈值拒掉的那 1 条描述性查询。）

**为什么第一版没测出来**：因为测试只覆盖了**召回**（"能查到吗"），
从没覆盖**拒识**（"该查不到的时候查到了吗"）。
`test_map_query_min_score_filters_irrelevant` 用了"宇宙飞船"这种
与所有标签 bigram 完全不重叠的词，所以任何正值阈值都能通过 ——
**测试用例选得太"友好"，等于没测**。

**教训**：
1. **默认值"看起来能用"不等于"没有假接受"** —— 要主动构造**对抗性负样本**
   （共享少量 n-gram 的词），而不是只测明显不相关的词；
2. **拒识率必须和召回率一起进指标**，而且要作为一个**独立的评测维度**写进脚本，
   不能指望零散的单测覆盖；
3. **模糊匹配那一层的分数上限，决定了下限阈值的合法区间** ——
   阈值必须高于噪声层上限、低于真信号下限，这个区间是设计出来的，不是试出来的；
4. 已加回归锁 `tests/test_query.py::test_lexical_threshold_rejects_ngram_noise`
   和 `test_lexical_threshold_keeps_legitimate_hits`（后者防止把阈值抬过头误杀真命中）。

### 2.2c ★ 自监督阈值标定：能推广的和不能推广的

**背景**：2.2b 修好了词法阈值、4.5 修好了嵌入阈值，但两者都是**离线扫出来的常量**。
换个数据集/编码器就得重扫 —— 治标。

**转机**：地图建好后，**每个物体都带着检测器给的标签**。这份数据自带，不需要额外标注。
它足以回答一个更弱但够用的问题：
*物体 i 对**自己**的标签，是不是比对**别的**标签得分高？* 能回答这个就能定阈值。

**做法**：拿地图自己当标定集 —— 每个不同标签当查询词，走**和真实查询完全相同**的
打分路径；对自己物体的分数是正样本，对其它物体的分数是负样本；
在候选阈值上**最大化平衡准确率** `TPR + TNR`。

用平衡准确率而非准确率，是因为正负样本是 `N : N(U−1)` 极不平衡，
用准确率的话"全部接受"就能拿高分。并列最优时取**更大的**阈值。

**结果（嵌入侧成功）**：

| 纯嵌入方案 | 命名类 | 描述类 | 拒识率 | 综合分 |
|---|---|---|---|---|
| 硬编码常量 0.0005 | 31.5% | 12.5% | 87.5% | 0.232 |
| **自监督标定（逐场景）** | **41.4%** | 12.5% | 86.1% | **0.291** |

阈值范围 7.2e-05 ~ 2.4e-03，逐场景自适应，换数据集不用重扫。

**踩的坑**：第一版标定用底层 `pair_scores` 算分数，但查询走的是
`EmbeddingMatcher`（带提示词集成 + 空文本校准），**两者不在同一尺度上**，
标出来的阈值没法用。必须复用查询时那条路径。
这与 2.2b 上方"评测脚本混了视图"是**同一类错误**：
**同一个打分逻辑有两处独立实现，就一定会漂移。**

**否定实验（词法侧失败，但更有价值）**：很自然想把这套推广到词法侧，实测**变差**：

| 路径 | 标定集分离度 BA（上界 2.0） | 标定阈值 | 综合分 |
|---|---|---|---|
| 词法 | **2.000** | 0.90~0.95 | 0.828 → **0.742** ↓ |
| 嵌入 | 1.33~1.50 | 7e-05~2.4e-03 | 0.232 → **0.291** ↑ |

**根因**：词法标定集是"标签查自己" —— 别名表对自身必然 1.0、对别的≈0，
正负样本**完全可分**，优化器把阈值推到正样本分布最边缘（≈0.90）；
而真实查询（"杯子"、"seat"）常只落在**子串那层 0.85**，全被误杀。
嵌入标定集的分布本就重叠（BA≈1.4），阈值落在有意义的间隙里，所以泛化好。

**教训（可推广的判据）**：
1. **自监督标定只在「标定集难度 ≈ 部署难度」时才有效。**
   标定集比真实场景简单 → 阈值必然过严。
2. **平衡准确率接近上界 2.0 是"标定集太简单"的危险信号，不是成功信号。**
   在标定集上看着像满分，恰恰说明它没在回答真问题。
3. 这与"评测脚本混视图"是同一思维陷阱的两面：
   **都是用一个比真实场景更容易的东西去代表真实场景。**
   现在应该反问：**"我这个验证集，是不是比真实情况简单？"**
4. 回归锁 `test_lexical_threshold_is_not_auto_calibrated` 把这个否定结论固定下来，
   免得以后有人"顺手"把标定推广过去。

### 2.2d ★ TF 位姿接线：两个"只有真 tf2 才会暴露"的 bug

**背景**：ROS2 链路在 RoboStack（Windows 原生）上早就跑通了。
但 **RoboStack 没有 `tf2_ros`**，测试 `--pose auto` 会自动退回 odometry ——
**整条 TF 路径被绕过**。直到装上 WSL2 + ROS2 Humble 跑真 tf2，问题才现形。

初版现象：**处理了 6 帧、位姿失败 0 帧，却建出 0 体素**。

#### 定位过程（值得记的方法）

1. **先做对照实验，而不是猜**：同一个 WSL 环境里跑 `--pose odometry` → **通过**
   （461 体素 / 3 物体）。于是锁定"问题在 tf 路径，与环境无关"。
2. **隔离诊断**：写 `13_diag_tf_pose.py`，用同一棵静态 TF 树做**四组配置对照**
   （A 查 optical 不纠正 / B 查 link 做纠正 / C 查 optical 又纠正 / D 查 link 不纠正）。
   判据不是"哪组对"，而是 **A 与 B 必须一致** —— 同一个物理相机两种描述方式，
   结果必须相同。这个判据同时验证了 `R_OPTICAL_TO_LINK` 矩阵本身。
3. **加探针取数据**：在 `add_frame` 前打印 `frame.pose`，
   一眼看到 **`pose_t=[0,0,0] pose_R0=[1,0,0]`（恒等位姿）**。

#### Bug 1（根因）：`stamp` 类型不匹配 → 静默回退恒等位姿

| 环节 | 事实 |
|---|---|
| 项目内部约定 | `PoseProvider.get_pose(stamp)` 的 stamp 是 **float 秒**（`nodes.py` 用 `_stamp_to_seconds(...)`；`TrajectoryPoseProvider` 也 `float(stamp)`） |
| tf2 要求 | `lookup_transform()` 只接受 `rclpy.time.Time` |
| 直接传 float | **抛异常** |
| 而 `build_pose_provider` | 配了 `fallback=IdentityPoseProvider(warn=False)` → **异常被吞、退回恒等位姿** |
| 于是 | 帧带着恒等位姿建图；`pose_failures` 依然是 0（位姿"拿到了"，只是完全不对） |

**这个 bug 最阴的地方**：它把"查询失败"伪装成"查询成功"。
失败信号（异常、计数器）全被兜底吃掉了，只剩一个看起来正常但完全错误的结果。

**修**：新增 `_stamp_to_ros_time()`（float/Time/None 三种输入都接受）；
并把 **identity 兜底改成默认关闭**（需显式配 `deploy.ros2.pose.fallback_identity: true`）。
理由：它直接违反 `nodes.py` 自己写明的原则 ——
**"宁可丢帧，也不要用恒等位姿凑数"**（错误位姿污染整张地图，事后极难归因）。

#### Bug 2：`optical_frame_correction` 被套用两次

`ros2_e2e_test.py` 里注释和代码自相矛盾：注释写"指向标准 optical frame，
所以**不需要**轴纠正"，代码却写 `optical_frame_correction = (args.pose == "tf")` → `True`。
查的既然是 `camera_color_optical_frame`，就是光学系位姿，再纠正一次 = 重复旋转。

量化（诊断脚本输出）：

| 用例 | 配置 | 与期望位姿误差 |
|---|---|---|
| A | 查 optical frame，**不**纠正 | **0.000000 m** ✅ |
| B | 查 camera_link，**做**纠正 | **0.000000 m** ✅ |
| C | 查 optical frame，**又**纠正 | **1.697 m** ❌ |
| D | 查 camera_link，不纠正（对照） | 1.697 m ❌ |

**A vs B 平移差 = 0.000000 m** → 矩阵是对的，错的只是配置。

#### 修复后

```
位姿方式: tf | 已处理 6 帧 | 位姿失败 0 | 461 体素 → 3 物体
table 0.534m / chair 0.239m / cup 0.053m   3/3 次稳定 PASS
```

**与 odometry 路径逐位一致** —— 两套独立位姿来源产出完全相同的地图。

#### 教训

1. **"只在一条路径上测试"等于没测另一条**。Auto 降级机制（没有 tf 就用 odom）
   让 CI 永远绿，却把整条路径的真实性掩盖了。
2. **兜底逻辑会吃掉故障信号**。任何 "except → 用默认值" 都要问：
   *这个默认值是安全的吗？* 恒等位姿在这里就是"看起来对、其实全错"。
3. **调试探针本身也会引入 bug**：我给测试加探针时用了 `frame.depth`
   （实际是 `frame.depth_m`），`AttributeError` 冒泡到 rclpy 的 spin 线程，
   让测试变成"0 帧处理"，反而更难查。
4. **对照实验 > 猜测**。如果一上来就盯着位姿矩阵推导，大概率会怀疑
   `R_OPTICAL_TO_LINK` 写错了 —— 而它其实是对的。四组对照一次就定位到配置。

### 2.3 别名表反向索引必须多对多

**现象**：查询"桌子"命中了 `desk`，但地图里明明有个 `table`。

**根因**：构建反向索引时用单值 dict：
```python
_ALIAS_TO_CONCEPT[alias.lower()] = concept    # ← 后写入的覆盖先写入的
```
"桌子" 同时在 `table` 和 `desk` 的别名表里，字典迭代顺序让 `desk` 覆盖了 `table`。

**解法**：改成 `Dict[str, set]`（别名 → 概念集合），
并且 `_resolve_labels` **保留歧义** —— 返回全部达标标签，
按「提及顺序 → 分数降序 → 地图标签顺序」排序，而不是 `argmax` 硬选一个。

**为什么保留歧义更好**："桌子上有什么" 如果地图里同时有 desk 和 table，
用户其实想知道两者；硬选一个会漏掉一半信息。

## 三、推理层

### 3.1 "旁边(near)"几乎不可达

**现象**：设计里支持 `near` 关系，但实际上几乎永远不触发。

**根因**：关系判定用"归一化分离量"，用两个物体的平均尺寸做尺度。
要让 `norm < axis_ratio(0.15)` 同时 `bbox_gap > 0`（不重叠），
需要"两个物体很大但只分开一点点"—— 很罕见。

**第一次尝试（错的）**：加规则"间隙 ≤ 阈值 → near"。
**立刻踩坑**：杯子放在桌上时 `bbox_gap = 0`，
于是"杯子在桌子**上面**"被误判成"杯子在桌子**旁边**"。

**最终解法**：**只在水平轴做"相邻→near"判断**。
```python
if axis == 2:            # 竖直：接触就是 above/below，不是 near
    return above/below
if bbox_gap <= adjacent_gap:   # 水平：表面间隙 ≤ 15cm 算"旁边"
    return "near"
```

**语义依据**：口语里的"旁边/挨着"是**水平**概念；
竖直方向上的接触关系是"在……上面"。

**回归测试**：`test_relation_above_not_overridden_by_near`
—— 这个测试是专门为这个 bug 留的，改阈值时必须过。

---

### 3.2 中文意图解析不切词，用词表召回

**问题**：中文没有空格，正则切词极易出错
（"桌子上有什么" 用空格切会得到一个整体）。

**方案**：**不切词，直接子串召回**。
1. 构造词表 = 全部别名 + 地图标签（**不是只有地图里有的**）；
2. 按长度降序扫描原文，用区间占用避免重复匹配（长词优先）；
3. 召回到的提及再映射到地图里真实存在的标签。

**关键点**：词表必须是**全量别名表**而不是"地图内类别"。
否则"杯子在哪"（地图里没有杯子）会召回到 0 个提及，
意图被判成 `describe`（描述场景），而不是 `locate` + "没找到杯子"。
**"没找到"和"答非所问"是完全不同的用户体验。**

---

### 3.3 歧义标签排序需要稳定的 tie-break

`np.argsort(-scores)` 对同分元素顺序不保证（虽然默认是 quicksort，不稳定）。
改成 `np.argsort(-scores, kind="stable")`，
让"地图标签顺序"（按频次排序）成为同分时的 tie-break。
这样"桌子"在同时有 desk 和 table 时，会优先选地图里更常见的那个。

## 四、部署

### 4.1 FP16 模型必须配 FP16 输入

**现象**：`compare_quantization(modes=("none","fp16"))` 里 fp16 那一行失败：
`mat1 and mat2 must have the same dtype, but got Float and Half`。

**根因**：把模型转 FP16 后，输入张量还是 FP32。这是量化实践里最常见的坑。

**解法**：工具层自动处理，而不是把这个负担丢给调用方。
```python
model_dtype(model)               # 只看浮点参数（忽略量化后的 qint8 权重）
cast_inputs_to_model(model, x)   # 自动转换
```
`compare_quantization` 内部对每个模式都重新构造输入并按 dtype 转换。

**注意**：动态 INT8 量化后，权重是 `qint8`（非浮点），
所以 `model_dtype` 必须**跳过非浮点参数**，返回 bias 的 fp32 才对。

---

### 4.2 异步流水线的价值是"解耦"不是"并行"

Python 有 GIL，多线程跑 CPU 密集任务并不会真的并行。

**所以这个模块的定位要说清楚**：
- ✅ 它解决的是"慢任务（VLM）不阻塞实时链路（感知）"；
- ❌ 它**不是**并行加速器。

**真正的并行需要多进程** —— 但本项目是 8GB 单卡场景，
多进程会重复加载模型、重复占显存，得不偿失。

**设计要点**：
1. 队列满时**丢最旧的帧**，绝不阻塞实时链路；
2. 慢档读的是地图**快照**，避免读到写一半的状态；
3. 两档独立统计 p50/p95，便于定位瓶颈；

**测试踩坑**：测"队列满丢帧"时，需要让 fast_fn 卡住才能在队列里堆积。
用了一个 `gate` 标志位控制 —— 这类并发测试必须能确定性地制造拥塞，
不能靠 `sleep` 猜。

## 五、评测与数据

### 5.1 检测 IoU ≈ 0 是**预期**的，不是 bug

**现象**：基准报告里 `mean_iou@0.25 = 0.0000`，看起来像系统坏了。

**根因**：离线后端的 `BoxSegmenter` 把 bbox 直接当掩码。
反投影时框内的**背景点**（地面、墙）也被纳入 3D 包围盒 →
预测框显著偏大 → IoU 接近 0。同时预测框的朝向被近似为 0（GT 有 yaw）。

**处理方式（而不是掩盖）**：
1. 保留这个指标（它诚实地反映了 bbox 基线的上限）；
2. 在报告里**自动加一条说明**解释为什么低；
3. 新增 `map_localization`（物体级中心误差）作为**主要质量指标** ——
   因为机器人真正消费的是"地图里的物体在哪"，不是"单个检测框的 IoU"。

**叙事价值**：这组对比正好论证了"应该用 SAM 精细掩码替换 bbox"这个判断。
**把缺陷量化出来，比藏起来有价值得多。**

---

### 5.2 用"角点闭环"作为几何正确性的金标准

**问题**：怎么证明渲染器 + 位姿约定 + 反投影三者的组合是正确的？
单独测每一个都可能"各自都对、组合起来错"。

**方案**：构造一个**闭环**，用不变量断言。
```
GT 角点 --位姿--> 相机系 --投影--> 像素 --读深度--> 反投影 --> 相机系 --逆位姿--> 世界系
                                                                              ↓
                                                        与 GT 角点比较，误差必须很小
```

在合成场景里要求 **>95% 的实例像素反投影后落在 GT 盒内**
（`test_synthetic.py::test_unprojected_instance_pixels_fall_inside_gt_box`）。

这个测试同时覆盖了三个组件的组合正确性 —— 任何一个错了都会失败。

---

### 5.3 真实数据测试必须"挑对场景"

**现象**：`test_auto_labeler_on_real_data` 失败，`num_candidates == 0`。

**根因**：测试随手取了前 3 个场景，而 SUN RGB-D 里大量场景只有
bed/cabinet/dresser，**不含**测试 prompts 里的 chair/table/desk/monitor。
stub 检测器是按 prompt 过滤的，所以一个都检不出来。

**解法**：测试必须**按内容选场景** ——
先查索引里的 `label_flat`，只挑含目标类别的场景。

**教训**：真实数据集的类别分布极不均，
任何"随机取 N 个样本"的测试都可能偶然失败。要么按条件筛，要么固定 seed 并验证过。

### 5.4 ★ ROS2 验证脚本的匹配逻辑让指标虚高（2026-09-12 发现）

**现象**：ROS2 端到端测试长期报告"物体定位误差 **table 0.209 m**"，
而换成按标签严格比对后，table 的真实误差是 **0.534 m**。

**根因**：验证脚本的匹配逻辑写成了"**对每个地图物体，找最近的 GT**"，
**但没有检查标签是否一致**：

```python
for obj in objs:                       # 遍历地图物体
    for gt_label, gt_c in gt:          # 找最近的 GT —— 不看 label
        d = norm(center - gt_c)
        best = min(...)
    print(f"{obj['label']} 误差={d:.3f}")   # 却用地图物体的标签去打印
```

实际数据恰好能说明问题：

| 地图物体 | 质心 | 到 table GT (2.0,−0.3,0.4) | 到 cup GT (1.70,0,0.85) |
|---|---|---|---|
| `table` | (1.78, 0.10, 0.68) | 0.534 m | **0.213 m** ← 更近 |
| `chair` | (2.22, 0.59, 0.61) | — | — |
| `cup` | (1.74, 0.04, 0.85) | — | 0.051 m |

table 的地图质心**离 cup 的 GT 更近**，于是脚本把 table 这一行
**匹配到了 cup 的答案**，报出 0.209 m。看起来精度很好，实际是**张冠李戴**。

**为什么危险**：这不是"算错一个数"，而是**让指标系统性虚高** ——
只要有一个物体被错误匹配到一个更近的异类 GT，它的误差就会被"修正"成好看的值。
而且它**不报错**，输出格式完全正常。

**发现路径**：写 rosbag 端到端测试时，用**独立实现**做了同样的比对，
得到 0.534 m —— 两个脚本对同一份地图给出不同数字，才暴露出来。
**独立复现是对抗这类"自证式指标"的唯一手段。**

**解法**：改成**按标签匹配**（只认同名物体），并打印未匹配的标签。
修正后三种位姿来源（static / tf / odometry）给出**完全一致**的
`table 0.534 / chair 0.239 / cup 0.053`。

**教训**：
1. **验证脚本本身也是要被验证的代码** —— 它和被测代码一样会错，
   而且错了**只会给你一个好看的数字**，不会报错。
2. 凡是"匹配/对齐"逻辑，必须显式检查**语义键**（这里是 label），
   不能只按几何近邻 —— 近邻在天生相近的类别之间必然张冠李戴。
3. **同一件事用两份独立实现算**，不一致就是线索。

> 顺带修掉另一个：`--pose static` 模式**从引入起就是坏的**（建图 0 物体）。
> 原因是我先前把 `optical_frame_correction` 无条件改成 `False`，
> 但 static 模式的 `translation`/`rpy` 描述的是 **`camera_link`** 而不是光学系，
> **需要**轴纠正。之所以一直没发现，是回归只跑 `auto`
> （在 WSL 选 tf、在 RoboStack 退回 odometry），**static 这条分支从没进过回归**。
>
> **教训：一个模式有 N 条分支，只测一条 = 其他 N−1 条都是未知状态。**

## 四点五、部署层（ROS2）—— 四个"静默错"与一个"测量工具骗人"

> 这一节是 2026-09-12 把项目**真正打成 ament 包**（`colcon build` + `ros2 run` +
> `ros2 launch` + 参数服务）时才暴露出来的。共同点：
> **每一个都不报错、单测全绿、离线看不出来**，
> 只有"在真 ROS2 里跑一遍并核对数值"才会露出来。

### 4.5.1 参数接到了一条**没人读**的 Config 路径

`PARAM_MAP` 把 `min_depth` 接到了 `deploy.ros2.min_depth`，
而 `nodes.py` 读的是 `geometry.min_depth`。
于是 `ros2 param set /perception min_depth 0.3` **无声失败** ——
参数服务说"成功"，算法还用 0.1。

同一类错误还有两处（都是"配了不生效"）：

| 位置 | 写成了 | 真实键 | 后果 |
|---|---|---|---|
| `nodes.py` | `deployment.ros2.topics` | `deploy.ros2.topics` | 话题名在 YAML 里配了完全没用 |
| `nodes.py` | `cfg.get("data.auto_label_min_points")` | **不存在** | 默认配置里没这个键，YAML 里配不了 |
| QueryNode | `reasoning.vlm.enabled` | **不存在** | VLM 开关只能靠代码设，配置文件里看不见 |

**根因**：`cfg.get(path, default)` 的语义是"路径写错永远不报错，只会悄悄用 default"。
这类 bug 单元测试抓不到（行为"正常"），**只有把"路径存在性"本身当断言**才能抓住。

**解法**：
1. 补进 `DEFAULT_CONFIG`（让每个开关都在配置里看得见）；
2. 新增 `tests/test_config_paths.py`：扫描 `src/**` 的 `cfg.get/set("...")`，
   逐个断言路径在 `DEFAULT_CONFIG` 里真实存在；
3. 单独断言 ROS2 `PARAM_MAP` 的每个目标路径存在。

> 这个测试第一次跑就抓出 4 个生产代码里的幽灵键。
> **教训：凡是"字符串键 + 兜底默认值"的 API，都要有一条测试专门守键的合法性。**

### 4.5.2 "用另一个名字的节点读参数"是个静默陷阱

早期实现：起一个 `roboground_param_bootstrap` 节点声明参数、算出 Config，
销毁它，再用真正的 `perception` 节点跑。

`--params-file` 的顶层键就是**节点名**，必须与运行时节点名完全一致。
实测（`scripts/wsl/42_probe_param_matching.py`）：

```
参数文件键 = perception，节点名 = perception                 → 取到 0.77  ✓
参数文件键 = perception，节点名 = roboground_param_bootstrap → 取到 0.05  ✗（默认值）
```

也就是说 bootstrap 读到的是**默认值**、真节点读到的是**文件里的值**，
两者静默不一致；而且参数声明在 bootstrap 上，
`ros2 param set /perception ...` 对**真节点完全无效** ——
"支持在线调参"这句话在最关键的地方是假的。

**解法**：让**真正干活的节点自己声明参数**（`deployment/ros2/params.py` 的
`declare_params`）。顺带解决了三件事：
参数服务看得到真实值、`param set` 真能生效、冷参数会被**拒绝并说明原因**。

> 顺带一个反直觉的结论：`params_file` **支持 `/**` 通配键**，
> 但不支持按节点名后缀匹配。这条也是实测出来的，不是查文档猜的。

### 4.5.3 "启动竞态"让前几帧被静默丢掉

`TfPoseProvider.setup()` 原来自报"TF 已就绪"，但它**只创建了 listener**，
一条 `/tf` 都还没收到。真机启动顺序经常是"感知节点先起、TF 树后到"，
于是开头若干帧位姿查不到 → **被丢弃**（丢帧本身是对的：宁可丢帧不伪造位姿，
但"能等就不该丢"）。

实测证据：完整 TF 树端到端里 **6 帧只处理了 5 帧、1 次位姿失败**。

**解法**：把日志改成诚实的措辞（"TF 监听器已创建"），
并新增 `wait_ready(timeout_s, spin_once=...)`：
启动期用 `rclpy.spin_once` 转几次回调，等到真的能查到再开始收数据
（此刻还没 `start spin`，自己转是安全的）。
超时就明确告警，并说明"后续帧会被丢弃"。修完 **6/6 帧、0 失败**。

> **教训：日志说"就绪"之前，先确认它真的就绪了。**
> 一句过于乐观的日志会把一个可修的竞态变成"偶尔少几帧"的玄学问题。

### 4.5.4 launch 文件里 `LaunchConfiguration` 拼进节点名 → 整棵树起不来

```python
name=f"tf_{index}_{child}"     # child 是 LaunchConfiguration，不是字符串
```
→ `Invalid node name: node name must not contain characters other than
alphanumerics or '_'`，四条边一条都发不出来。

这个**只有真跑 launch 才会发现**（`--show-args` 是好的，
静态检查也看不出来）。教训是：
**交付物（launch 文件）必须被真的执行过一次**，
不能只验证"我脚本里广播的 TF 是对的"。

### 4.5.5 ★ 测量工具本身骗人：两个错误叠加得出"完全错误"的结论

第一版延迟脚本得出"单帧 553 ms、10 Hz 丢帧 20%、跑不到 10 Hz"。
**这个结论是错的**，错在两个测量 bug 叠加：

1. 包了 `builder.add_frame` 却**忘了注入 GT 框** ——
   而 `stub` 检测器靠 `frame.meta["boxes_3d"]` 拿目标，没注入就自己按 prompts
   造了 15 个框（真值 3 个）→ 工作量被放大 5 倍；
2. 用 `node._sync.registerCallback(wrapper)` 打点 ——
   `message_filters.registerCallback` 是**追加**语义（内部
   `self.callbacks[len(...)] = (cb, args)`），原来注册的回调**还在**，
   wrapper 里又调一次原回调 → **每帧被处理两遍**。

两个错误都让数字**看起来更"合理"**（"哦 Python 就是慢"），
所以极难察觉。修正后：单帧 42 ms、10 Hz 丢帧 **0.0%**。

**解法（现在都在代码里）**：
- 打点改成包 `process_frame`（公开方法，实例属性遮蔽类方法，只会调一次）；
- 加**自检断言**：`len(perceive_ms) == frames_processed`
  （一帧被处理两遍会当场暴露）；
- 分离"纯计算"与"ROS 链路"两档，并加"目标数伸缩"曲线 ——
  因为耗时**正比于目标个数**，脱离目标数报"单帧 xx ms"没有意义。

> **教训**：能跑出数字 ≠ 数字可信。凡是自建测量工具，都要有一条
> **"这个数字在什么情况下会失真"** 的自检，并且**用两条独立路径互相对账**
> （纯计算 vs 实链路）。

### 4.5.6 ★★ 单次测量得出的"0% 丢帧"活不过一次重启

上面修完之后，我把"**320×240 单帧 42 ms、10 Hz 丢帧率 0.0%**"写进了
README、AGENTS、面试QA、简历要点等 **18 处**。

**然后电脑重启了一次，重跑统一入口 —— 延迟那一项直接 FAIL：**

```
实测 10 Hz 丢帧率：10.0%      ← 同一台机器、同一份代码
→ FAIL  320×240 上限=21.07 Hz  10Hz 丢帧=10.0%
```

于是我把 10 Hz 那一档改成**重复 3 次**，并多跑了几轮，拿到 7 次测量：

| 机器状态 | ROS 链路单帧 | 10 Hz 丢帧率 |
|---|---|---|
| **冷启动（刚重启）** | **59.7 ms** | **10.0%** |
| 热机 ×5 | 40.1 / 40.2 / 40.8 / 41.9 / 42.5 ms | 0% ×5 |

**根因**：纯计算上限只有 **21~24 Hz**，对 10 Hz 需求只有约 **2.2 倍余量**。
余量这么小的时候，冷启动的页缓存未命中和进程竞争就足以把单帧从 42 ms
推到 60 ms（→ 有效能力 16.7 Hz < 10 Hz 到达率）→ 队列堆积 → 丢帧。
**不是我算错了，是"0%"这个结论本身没有余量支撑。**

**改法（两层）**：
1. **文档**：18 处全部改成范围与条件 ——
   「单帧 42~47 ms（上限 21~24 Hz）；10 Hz 热机 0% 丢帧、**冷启动实测 10%**，
   处于**能力边缘**」。并且明确写：要稳定达标得把单帧预算压到 ~20 ms 以内，
   而不是指望它刚好够。
2. **脚本**：把那条脆弱的检查删掉了。原来的 `"C 10 Hz 丢帧率与 A4 预测一致"`
   拿**一次**链路测量去对**一次**纯计算预测，本身就是不成立的判据 ——
   它这次正确地报红了，但报红的原因是噪声而不是缺陷。
   现在改成：10 Hz 档**默认重复 3 次**、只保留一条宽松下界
   （"没有整体崩掉"），真实能力靠**丢帧率分布 + 单帧耗时**陈述。

> **教训（这一节最值钱的一条）**：
> **一个"刚好达标"的数字不是一个结论，而是一次幸运。**
> 报性能数字时必须同时报**余量**（这里 2.2×）和**波动**
> （这里单帧 40→60 ms）。
> 余量小于 ~3 倍的指标，单次测量**不足以**支撑"达标"的结论，
> 必须重复测量看分布 —— 否则重启一次就会被打脸。
>
> 顺带：**这次是"重启"这个外部扰动帮我发现了问题**。
> 所以"复现验证"不该只在交付前跑一次，而该在环境变化后重跑 ——
> 我这次改完文档后，把这条写进了 `ros2_ws/README.md` 的验证清单。

## 六、工程实践

### 6.1 "离线降级"不是偷懒，是工程必需

一开始想只做真实后端，但很快发现：
1. 没 GPU 的机器上无法跑 CI；
2. "结果不对"时无法判断是几何错了还是模型错了；
3. 模型下载失败会让整个流程不可用。

所以每个重模型后端都配了降级实现，**但都明确标注了代价**
（见 README 的"已知局限"和本文档的 5.1）。

### 6.2 Windows 控制台中文乱码

`print()` 中文在 GBK 控制台会变乱码。
在 `utils/logging.py` 导入时把 stdout/stderr 重配成 UTF-8：
```python
stream.reconfigure(encoding="utf-8", errors="replace")
```
失败就静默忽略（不影响功能）。

### 6.3 内参尺寸不一致必须早失败

`depth_to_points_camera` 检查 `intrinsics.width == depth.shape[1]`，
不一致直接抛异常。

**为什么**：resize 图像后忘了同步缩放内参，会导致投影全错，
但**不会报错** —— 错误会飘到几百行之后，表现为"精度莫名很低"。
用一个显式的检查把它变成"立刻失败"。
