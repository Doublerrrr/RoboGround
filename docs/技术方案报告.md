## 一、问题定义与难点

### 1.1 形式化

| 项  | 定义                                                    |
| -- | ----------------------------------------------------- |
| 输入 | RGB-D 帧序列 $\{(I_t, D_t, K_t, T_t)\}$ + 自然语言 query $q$ |
| 输出 | 目标物体的 3D 中心 $c \in \mathbb{R}^3$（米）+ 尺寸 + 标签 + 空间关系   |
| 约束 | 端侧实时（感知 ≥10Hz）、8GB 显存、类别集开放、环境未知                      |

### 1.2 三个核心难点

**难点 1：类别开放（open vocabulary）**  
用户可能问任何物体（"那个放饮料的东西"）。封闭集检测器的 label 集合覆盖不了，  
所以必须用**文本与视觉共享空间**的表示（CLIP 范式），  
并且 3D 侧也要存特征而不是类别 id。

**难点 2：环境未知（online mapping）**  
机器人第一次进这间房，没有预先建好的地图。所以必须在线增量建图，  
并具备**多视角融合**能力（同一物体被多帧看到 → 特征平均 → 抗噪）。z

**难点 3：实时性（latency budget）**  
VLM 推理动辄几百 ms~~数秒，而避障需要 10~~30Hz。  
两者不能串在一个循环里，必须**按时间轴分级**。

### 1.3 与纯 2D VLM 的本质差异

| 维度     | 2D VLM        | 本项目（3D 语义地图）                       |
| ------ | ------------- | ---------------------------------- |
| 空间表示   | 像素坐标          | **米制 3D 坐标**                       |
| 能否给规划用 | ❌ 不知道"1.5 米外" | ✅ 直接输出 `geometry_msgs/PoseStamped` |
| 多视角一致性 | 无             | 体素级特征融合天然一致                        |
| 遮挡处理   | 看不到就没了        | 多帧累积可"回忆"                          |
| 推理成本   | 单次几百 ms       | 感知 ~38 ms/帧 + 查询 0.33 ms（§4.2）      |

**结论**：机器人动作规划需要**带尺度的语义**，  
而 2D VLM 只给"像素级语义"。所以必须把语义升维到 3D —— 这是本项目的立足点。

### 2.2 实现映射：每一步用什么模型 / 算法

> 与上图**同一套步骤编号**，但每个方框标注的是**具体实现**：
> 用了哪个模型、哪个纯算法、代码在哪个文件、关键超参是多少、离线怎么降级。
> 所有"默认"取自 `configs/default.yaml`（全离线：无权重 / 无网络 / 无 GPU 也能跑通全链路）。

```
① 输入 ─────────────────────────────────────────────────────────────
   ROS2: sensor_msgs/Image + CameraInfo ──► deployment/ros2/bridge.py
   离线: 2D-3D-S / SUN RGB-D ─────────────► data/stanford2d3d.py, data/sunrgbd.py

② 多视角 → 全景 【离线】data/panorama.py
   ★ 纯算法（无模型）：角度权重 cos^2 · 共识斜距融合 · np.bincount 归约
   默认 width=2048 height=1024 weight_power=2.0 min_cos=0.35 max_depth=8.0
        range_outlier_m=0.5 rgb_mode=weighted_mean
   中心校验：N 个视角共享光心（离散 >0.05 m 告警）

③ S1 开放词汇 2D 感知 【可插拔】perception/registry.py
   Detector  : stub(GT投影) │ grounding_dino(GroundingDINO) │ yolo(YOLO)
               默认 stub        box_threshold=0.30 text_threshold=0.25
   Segmenter : box(bbox 直接当掩码) │ sam(SAM)
               默认 box         sam 用 sam-vit-base
   Encoder   : color_hist(72维 HSV 直方图) │ dinov2(DINOv2) │ clip(CLIP) │ siglip(SigLIP)
               默认 color_hist  feature_dim=72
   ▶ 换 backend 只改一行 config；离线后端不需要任何权重

④ 几何层 【纯 numpy，无模型】geometry/projection.py + geometry/camera.py
   raw_depth_to_meters(raw, scale)  depth_scale=1000.0
   filter_depth_ghosts(percentile)  depth_trunc_percentile=99.0  ← 玻璃穿透的虚远点
   范围过滤 min_depth=0.10  max_depth=8.00
   unproject_pixels()  ★ 按 meta["projection"] 分派：
       针孔    p_cam = z·k            （z 深度）
       等距柱状 p_world = C + r·d(u,v)  （斜距）
   位姿变换 p_world = Rᵀ(p_cam − t)

⑤ S2 3D 语义地图 mapping/builder.py + geometry/voxel.py
   体素聚合 VoxelGrid.add_observation()
       fusion=mean │ max │ confidence_weighted   默认 mean
       voxel_size=0.05 m                           max_voxels=2,000,000
   跨帧实例关联 MapBuilder._associate()   ★ 本项目核心决策
       assoc_radius=0.60 m  assoc_iou=0.10  assoc_require_label=true
       （算法：标签兼容 + 中心距离/3D IoU 双判据 → _ObjectTrack）
   聚类成物体 cluster_points_dbscan()   cluster_eps=0.08  cluster_min_samples=3
       bbox 分位数裁剪 object_bbox_percentile=2.0（抗离群点）
       object_mode=association（推荐）│ clustering（降级）

⑥ S3 语言查询 + 空间推理
   匹配 mapping/query.py
       LexicalMatcher   词法三层打分：规范概念 1.00 / 子串 0.85 / 字符 bigram Jaccard ≤0.80
                        接受阈值 0.5（0.05→0.5 使拒识率 72.2%→100%）
       EmbeddingMatcher 物体特征 × 文本嵌入（需 clip/siglip 编码器）
       QueryEngine      两路融合：hybrid 综合分 0.834（词法 0.828 / 嵌入 0.232）
   推理 reasoning/rule_engine.py + spatial_relations.py
       RuleEngine   Intent.kind 共 7 类（源码 rule_engine.py 里的实际取值）：
                locate(定位) / distance(距离) / list_on(某物之上有哪些)
                count(计数) / nearest(最近) / relation(关系) / describe(概述)
                    无模型，纯规则 + 中文不切词的词汇召回
                    near_threshold=0.50 above_delta=0.10 inside_ratio=0.60
                    axis_ratio=0.15 adjacent_gap=0.15
       空间关系 center_distance │ bbox_gap │ containment_ratio │ dominant_relation
    VLM  reasoning/vlm.py（可选，默认关闭）
       VLMBrain      Qwen2-VL-2B-Instruct + LoRA，load_in_4bit=true max_new_tokens=256
       HybridReasoner ★「语义归 VLM、度量归几何」：VLM 只出语义，米制一律几何算

⑦ 部署 deployment/
   量化 quantize_model()  fp16 / int8（deploy.quantize=none 默认）
   ONNX export_to_onnx() + verify_onnx() 数值校验
   分级 AsyncPipeline  fast_tier_hz=10.0  queue_size=4（快档 10 Hz、慢档异步）
   ROS2  ros2/nodes.py + ros2/params.py + ros2/tf.py
         PoseProvider: Identity │ Static │ Trajectory │ Tf（tf2_ros 真实 TF 树）
         21 个参数可在线上调（HOT_PARAMS / COLD_PARAMS）
```

### 2.4 数据层：从「虚拟视角」到「真实多视角 → 一张全景」（本次重构的核心）

```
一个采集点（同一 camera_uuid，如 2D-3D-S 的 office_6）
  └─ N 个**真实**视角（各自内参 + 位姿，**共享同一光心**，实测离散 1e-07~6e-06 m）
       └─ fuse_to_equirect()   多视角 → 1 张 360° 等距柱状全景（RGB + 斜距）
            └─ frame_for_panorama() → RGBDFrame（meta["projection"]="equirect"）
                 └─ backproject_detection() 走**精确等距柱状**反投影
                      └─ MapBuilder → SemanticMap → 查询   ← 下游一行未改
```

| 模块 | 职责 |
|---|---|
| `data/stanford2d3d.py` | 2D-3D-S 适配器：位姿/内参/深度/语义/GT 读取 |
| `data/panorama.py` | 多视角 → 等距柱状全景融合（权重、共识融合、覆盖统计） |
| `data/pano_scene.py` | 采集点 → `PanoScene`（含 GT 框投影与**可见性**判定） |
| `geometry/projection.py` | `unproject_pixels()`：按 `meta["projection"]` 分派针孔 / 等距柱状 |

**为什么换掉虚拟视角**：旧做法把 SUN RGB-D 的**单帧**点云重渲染成 N 个视角，
那是同一份观测的重采样，**信息量不增加**（无效深度像素 42.8% → 77.0%）。
新做法方向相反：N 个真实观测融合到同一球面坐标系，信息量随视角数**真的增加**
（实测 office_6：6→12→24→48 视角，像素覆盖 19.7% → 51.6%）。

**两条反投影通路的语义差别（改错了会静默出错，所以写在这里）**：

| | 针孔（默认） | 等距柱状全景 |
|---|---|---|
| 像素 → 方向 | `d ∝ [(u−cx)/fx, (v−cy)/fy, 1]` | `az=(u+0.5)/W·2π−π`、`el=π/2−(v+0.5)/H·π` |
| `depth_m` 语义 | 沿光轴的 **z 深度** | 从光心起算的**斜距 r** |
| 反投影 | `p_cam = z·k` | `p_world = C + r·d_world(u,v)` |

> ⚠️ 等距柱状的仰角是 `sin` 关系、等效针孔是 `tan` 关系，两者只在光轴附近接近。
> 用针孔去反投影 360° 全景，远离光轴的部分会**系统性错位**，而且错得「很合理」。
> 实测代价：中位定位误差 0.3419 m → 1.3291 m（**+74.3%**，§4.3）。

### 2.5 数据契约（`roboground/types.py`）

全项目只认这几个类型，保证模块间可替换：

```
CameraIntrinsics  fx/fy/cx/cy + width/height（含 K 矩阵互转、缩放、裁剪）
CameraPose        R/t（world → camera），支持 from_sunrgbd 标定构造
RGBDFrame         color + depth_m(米) + intrinsics + pose + meta
Detection2D       label + score + bbox + mask + feature
Observation       Detection2D + points_world（感知层 → 映射层的桥梁）
SemanticObject    label + center + bbox + feature + confidence + voxel_ids
SpatialRelation   subject + relation + object + distance + evidence
ReasoningResult   answer + targets + relations + distances + backend
```

**坐标约定（全项目统一，改之前想清楚）**

- 相机系：OpenCV（x 右、y 下、z 前）
- 世界系：z 轴向上
- 外参：`p_cam = R @ p_world + t`（即 `CameraPose` 存 **world → camera**）
- 深度：对外一律用米；**例外**：等距柱状全景的 `depth_m` 是**斜距**（见 2.2）
- 全景等距柱状：`u = (az+π)/2π·W`、`v = (π/2−el)/π·H`，
  像素中心在 `(i+0.5, j+0.5)`（不写 `+0.5` 会带来约半像素的系统性角偏差）

## 三、核心算法

### 3.1 开放词汇 3D 特征场

**思路**（OpenScene / CLIP-Fields 范式）：  
把 3D 空间切成边长 $v$ 的体素，每个体素聚合落在它内部的所有像素特征，  
得到稠密的 3D 特征场。查询时用"文本特征 × 体素特征"的相似度定位。

**为什么用体素而不是纯点云**：

1. 点云稀疏冗余（一个物体几万点，语义只有一份）；
2. 体素聚合天然完成**多视角融合**（同体素被多帧看到 → 特征平均 → 抗噪）；
3. 体素键是整数，便于哈希、连通域分析和序列化。

**三种融合模式的取舍**：

| 模式                    | 公式                                           | 适用                      |
| --------------------- | -------------------------------------------- | ----------------------- |
| `mean`                | $\frac{\sum w_i f_i}{\sum w_i}$（$w_i=1$）     | 通用，抑制单帧噪声               |
| `max`                 | 逐维 $\max_i f_i$                              | 保留最显著语义响应（OpenScene 常用） |
| `confidence_weighted` | $\frac{\sum s_i f_i}{\sum s_i}$，$s_i$ 为检测置信度 | 检测质量差异大时                |

**实现要点**：帧内先用 numpy 做一次聚合（`_unique_rows` 用 void 视图压行），  
再把"唯一体素"并入字典。这把 Python 层操作从 $O(N_{点})$ 降到 $O(N_{体素})$。

### 3.2 跨帧实例关联（★核心决策）

**为什么不用空间聚类**：DBSCAN 只看几何距离，  
桌子边上的杯子（中心距离 0.07m < eps 0.08m）会被连进桌子那一簇。  
消融实测（`scripts/42_ablate_association.py`，12 个真实采集点）：换成聚类后
命中率 **95.1% → 66.1%**、幽灵物体 **1.8% → 28.6%** —— 这一步是承重的，不是装饰。

**两条关联路径**（`mapping.assoc_strategy`，详见 `docs/消融与证据报告.md` §三）：

| 策略 | 规则 | 一帧内一条轨迹能否认领多个观测 |
|---|---|---|
| `hungarian`（**默认**） | 逐帧**全局最优**一对一分配（`scipy.optimize.linear_sum_assignment`） | 否 |
| `greedy`（旧行为） | 逐观测挑当前最高分轨迹 | 能 |

两者**共用同一个打分函数** `MapBuilder._match_score`，唯一区别就是上表最后一列：

```
score(obs, track):
    标签不兼容            →  −1（不允许）
    d = ||obs.centroid − track.center||
    d <= assoc_radius     →  1 − d/assoc_radius
    IoU >= assoc_iou      →  IoU               （assoc_iou > 1 表示关闭这条兜底）
    否则                  →  −1
```

`hungarian` 把"不分配"也做成一个选项：代价矩阵右侧补 `n_o` 个得分为 0 的哑列，
非法配对给 `−1e6`，于是"把观测空着"永远优于"硬塞一个非法配对"。

**为什么换默认**：`greedy` 下轨迹容量不限，同一帧的两个观测可以落进同一条轨迹。
当 A 更想进 T1、而 B **只能**进 T1 时（B 离 T2 超过半径），贪心会把两者都塞进 T1，
轨迹代表的物体中心就被拉偏。消融实测（12 个采集点均值）：

| 指标 | `greedy`（旧默认） | `hungarian`（新默认） |
|---|---|---|
| 碎裂率（产出物体数 / 应得物体数） | 0.79 | **1.04** |
| 命中率 | 95.1% | **98.1%** |
| 中心误差中位 | 0.5018 m | **0.4251 m**（−15.3%） |
| 关联耗时（40 物体 × 12 观测/帧 × 30 帧） | 21.05 ms/帧 | 20.31 ms/帧（**无可测回归**） |

单元测试 `tests/test_association.py::test_hungarian_beats_greedy_on_a_regret_case`
把这个失效模式钉成了解析例子：同一个场景里贪心的轨迹中心误差 0.1667 m、
最优分配 0.0250 m（6.7 倍）。

**同帧重复检测的合并**（`mapping.assoc_merge_iou`）：等距柱状全景里跨 ±180° 的物体会被
拆成两个 bbox，于是**一个物体在一帧里产生两个检测**；一对一分配会把它算成两个物体。
关联前先合并两条判据之一命中的观测：① 图像左右边界接缝签名（一段贴 `u=W−1`、
一段贴 `u=0` 且竖直区间重叠）；② 两团点云的轴对齐 3D IoU ≥ 0.5。
⚠️ 接缝**不能**用 IoU 代替：天花板/墙这类又宽又靠近极点的物体，两段在 3D 里
位于房间两侧，IoU ≈ 0（第一版就是这么写的，实测无效）。
修完"有几个 X"这类计数准确率 **60% → 93.9%**。

**标签兼容性判定**：复用 `LexicalMatcher` 的别名表——  
"chair" 与 "chair" 兼容，"cup" 与 "table" 不兼容。  
（这一步让"桌上的杯子"不会因为距离近而被并进桌子。消融：去掉它命中率 95.1% → 76.7%。）

**轨迹聚合**：用可累加的中间量而不是最终值  
（`points_sum/count` 求中心、`feature_sum/weight_sum` 求特征、  
`label_votes` 投票、有界采样的点集求分位数 bbox）。

### 3.3 空间关系判定

**主轴主导原则**：人描述位置时只说一个主导方向  
（"杯子在桌子上面"，不会说"上面偏右一点"）。

```
0) ★ 竖直方向完全不重叠（A 的最低点 ≥ B 的最高点）→ 直接判 above/below
   —— 放在主轴竞争之前，否则横跨房间的结构会被判成"在左边"
1) 包含关系优先：containment_ratio >= inside_ratio → "inside"
2) 计算三轴归一化分离量 norm[i] = Δ[i] / ((size_a[i]+size_b[i])/2)
3) 取 |norm| 最大的轴作为主导轴
4) 若强度 < axis_ratio → 退化为 near / overlapping / unknown
5) 竖直轴(z)：|Δz| >= above_delta → above/below；否则 near/unknown
6) 水平轴(x/y)：先看 bbox_gap <= adjacent_gap → "near"（相邻优先于弱方向）
              否则按符号 → left/right_of 或 in_front_of/behind
```

> 第 0 步是消融查出来的补丁：主轴竞争用的是**按物体尺寸归一化**的分离量，
> 天花板横跨整个房间，它与门的**中心**在水平方向差得很远，归一化后 x 轴反而占优，
> 于是"天花板在门上面吗"被答成"不是：天花板在门的左边"。
> 加上第 0 步后关系题准确率 50% → 85.7%（`scripts/43_eval_language_s3.py`）。

**为什么用尺寸而非固定阈值做归一化**：  
"两个大柜子相距 30cm"和"两个小杯子相距 30cm"是完全不同的语义。  
用两个物体的平均尺寸做尺度，判断才符合直觉。

**第 6 步的顺序很关键**：只在**水平轴**做"相邻→near"，  
否则"杯子放在桌上"（gap=0）会被误判成"杯子在桌子旁边"。  
（有专门的回归测试守护这条规则。）

### 3.4 语言查询：两路匹配 + 融合

| 匹配器                | 依赖      | 能力                   | 局限                       |
| ------------------ | ------- | -------------------- | ------------------------ |
| `LexicalMatcher`   | 无       | 别名表 + 子串 + 字符 bigram | **不是真开放词汇**，只能匹配别名表覆盖的表达 |
| `EmbeddingMatcher` | CLIP    | 真·开放词汇（任意文本）         | 需要模型与权重                  |
| 融合（hybrid）         | 可选 CLIP | 加权和 + max 兜底         | —                        |

**为什么用 max 兜底而不是纯加权平均**：  
两路分数尺度不可比（词法命中就是 1.0，嵌入相似度通常 0.7~0.9）。  
纯平均会让"词法强命中"被嵌入稀释。

**双语别名表**：~45 个概念 × 中英别名，反向索引必须是**多对多**  
（"桌子"同时属于 table 和 desk）。

### 3.5 意图解析（中文不切词）

**方案**：词表召回而非分词。

1. 词表 = 全部别名 + 地图标签（**全量，不限地图内类别**）；
2. 按长度降序扫描原文，用区间占用避免重复匹配；
3. 提及 → 地图标签的映射保留歧义（返回全部达标标签）。

**7 类意图优先级**：`distance > list_on > count > nearest > relation > locate > describe`

**关键设计**：判定"用户问了几个物体"用 `mentions`（含地图里没有的），  
判定"能不能回答"用 `matched_labels`（地图里真实存在的）。  
分开是必要的——否则"杯子在哪"（地图里没有杯子）会被误判成"描述场景"，  
而正确行为是回答"没找到杯子"。

> **「N ≤ 9 稳；N = 12 卡在线上；N ≥ 18 明显掉帧」**。

### 4.5 开放词汇查询评测（`scripts/16_eval_openvocab_query.py`）

**为什么要拆两个维度测。** "开放词汇"直觉上像"查询没见过的类别"，但直接这么测会得到平凡失败：  
地图物体来自检测器，**没被检测到的类别压根不在地图里**，查询必然落空 ——  
那测的是检测器的类别覆盖，不是查询接口的泛化能力。所以拆成：

- **未见表达命中率**：用**没在 prompts 里出现过**的说法指代**已建图**的物体；
- **未见类别拒识率**：查询**地图里没有**的类别时应返回空。

只看命中率会高估（永远返回"最像的东西"也有不错的命中率，但会指向错误位置）；  
只看拒识率会低估（什么都不返回自然 100% 拒识）。综合分 = **命中率 × 拒识率**。

命中率还必须**再按表达类型拆开**，否则同样会高估：别名表能覆盖"中文名/近义词"（命名类），  
但对"a thing to drink from"这类**描述性短语必然失败** —— 后者才是开放词汇的试金石。

**规模**：6 个合成场景 / 151 条未见表达（命名 111 + 描述 40）/ 72 条未见类别查询。

| 查询路径              | 命名类命中      | 描述类命中     | 拒识率        | 综合分       |
| ----------------- | ---------- | --------- | ---------- | --------- |
| 纯词法（别名表）          | **100.0%** | 35.0%     | **100.0%** | 0.828     |
| 纯嵌入（SigLIP）       | 31.5%      | 12.5%     | 87.5%      | 0.232     |
| **融合 hybrid（默认）** | **100.0%** | **37.5%** | **100.0%** | **0.834** |

**结论与一条实测出来的缺陷。** 初版默认词法阈值是 0.05，综合分只有 0.603 ——  
拒识率仅 72.2%，即**近三成的"地图里没有的类别"查询会返回一个错误物体**。  
根因是打分分层：概念命中 1.00 / 子串 0.85 / 字符 bigram Jaccard 上限 0.80，  
第三层是纯噪声（`bicycle` 与 `bottle` 共享 bigram `le`，Jaccard 0.09 → 0.145 分）。  
阈值抬到 0.5 后拒识率 100%、命名类命中率不降，综合分 0.603 → **0.828**；  
且扫描出的最优阈值恰好就是引擎默认值。已加回归测试锁定  
（`test_lexical_threshold_rejects_ngram_noise`）。

**嵌入侧的阈值必须就地标定，且要区分它在流水线中的角色。** SigLIP 声明的  
`suggested_pair_threshold = 0.02` 是在**检测区域特征**上量的，而查询比对的是  
**多视角融合后的地图物体特征**，后者分数尺度小约 20 倍。实测阈值曲线（纯嵌入路径）：

| 嵌入阈值             | 命名类   | 描述类   | 拒识率    | 综合分       |
| ---------------- | ----- | ----- | ------ | --------- |
| 5e-05            | 41.4% | 20.0% | 59.7%  | 0.214     |
| **5e-04（纯嵌入最优）** | 31.5% | 12.5% | 87.5%  | **0.232** |
| 0.001            | 27.9% | 10.0% | 91.7%  | 0.212     |
| 0.02（hybrid 最优）  | 3.6%  | 2.5%  | 100.0% | 0.033     |

同一个阈值在 hybrid 下最优、在纯嵌入下几乎全拒空 —— 因为**角色不同**：  
hybrid 里词法已负责接受判定，嵌入阈值退化为**精度过滤器**（收紧不损失命中、  
却减少假接受）；纯嵌入里它就是唯一的**接受阈值**（收紧直接砍召回）。  
两者最优值差 **40 倍**。现在由 `Encoder.suggested_pair_threshold` 与  
`Encoder.suggested_standalone_threshold` 分别承载，`QueryEngine` 按自身模式自动选择  
（地图上显式设了 `query_min_score_embedding` 时以用户为准）。

**一条关于评测本身的教训（比数字更重要）。** 本节的嵌入数字在第一版评测里是虚高的：  
评测脚本在**纯嵌入模式**下排序时误从样本里读了词法分数，于是量出来的"纯嵌入"  
混进了词法信号，报成命名类 78.4% / 描述类 25.0%。把排序视图改成与当前模式一致后，  
真实值是 **31.5% / 12.5%**。**评测脚本必须和被测路径共用同一套视图，  
否则量的是别的东西 —— 而且错的方向总是"看起来更好"。**

**阈值自标定：把"人工扫描"换成"自监督"（4.5 缺陷的根治）。**  
前面所有阈值都是离线扫出来的常量，换数据集/换编码器就得重扫。但地图建好后，  
每个物体都带着检测器给的标签 —— **这本身就是一份标定集**：  
物体对自己的标签应得高分、对别的标签应得低分。据此选阈值即可，无需任何 GT。

选点准则用**最大化平衡准确率** `TPR + TNR`（不用准确率：正样本 N 个、  
负样本是它的 U−1 倍，极不平衡）；并列最优时取**更大的**阈值（同样是满分宁可严一点）。

| 纯嵌入方案          | 命名类       | 描述类   | 拒识率   | 综合分       |
| -------------- | --------- | ----- | ----- | --------- |
| 硬编码常量 0.0005   | 31.5%     | 12.5% | 87.5% | 0.232     |
| **自监督标定（逐场景）** | **41.4%** | 12.5% | 86.1% | **0.291** |

标定阈值范围 7.2e-05 ~ 2.4e-03（每场景自适应）。**自监督标定优于硬编码常量**  
（综合分 +0.059），于是硬编码值降级为"标定不可行时的回退"（物体 <2 个、  
只有一个类别、编码器异常）。

⚠️ **标定必须走查询时完全相同的那条打分路径**（同一个 `EmbeddingMatcher.score`）。  
若用底层 `pair_scores` 直接标、却用 matcher 校准后的分数查询，两者不在同一尺度上 ——  
这与上一条"评测视图"是**同一类错误**：**只要有两处独立实现同一个打分逻辑，  
就一定会漂移。**

**否定实验：自监督标定不能无脑推广到词法路径。**  
很自然的下一个想法是"同一套 (标签, 标签) 打分，词法阈值也该能自标定"。  
实测**会变差**：

| 路径 | 标定集分离度 (BA，上界 2.0)     | 标定阈值            | 综合分                 |
| -- | ---------------------- | --------------- | ------------------- |
| 词法 | **2.000**（正负样本完全可分）    | 0.90 ~ 0.95     | 0.828 → **0.742** ↓ |
| 嵌入 | **1.33 ~ 1.50**（有明显重叠） | 7e-05 ~ 2.4e-03 | 0.232 → **0.291** ↑ |

根因是**标定集与部署分布不匹配**：词法标定集是"标签查自己"，  
别名表对自身必然命中 1.0、对别的≈0，正负样本**完全可分**，  
于是优化器把阈值推到正样本分布的最边缘（≈0.90）——  
而真实查询（"杯子"、"seat"）常只落在**子串那层（0.85）**，全被误杀。  
嵌入标定集的分布本就重叠，阈值落在有意义的间隙里，所以泛化得好。

**可推广的判据：自监督标定只在「标定集难度 ≈ 部署难度」时才有效；  
标定集比真实场景简单 → 阈值必然过严。**  
而**平衡准确率接近上界 2.0，正是"标定集太简单"的直接证据 ——  
在标定集上看着像满分，实际是危险信号。**

**诚实的边界。** 本基准只有 10 个类别且全部在别名表内，对词法路径**天然有利**；  
融合相比纯词法在描述类上只多命中 1/40 条（37.5% vs 35.0%），边际贡献很小。  
嵌入路径的真正价值要等词汇量超出别名表覆盖、或需要处理任意自然语言描述时才会显现 ——  
这也是"词法保底 + 嵌入扩展"分层设计的理由，而不是用嵌入直接替换词法。


### 4.6 区域语义与 VLM 空间问答

这一节直接对应岗位要求里的"视觉语言模型算法"。

**区域语义（`scripts/13_benchmark_region_semantics.py`）。** 用 SigLIP + 多裁剪 TTA  
对区域做开放词汇分类，分离"检测"与"编码"两个环节的贡献：

| 输入区域                    | Top-1    | Top-3    | MRR       |
| ----------------------- | -------- | -------- | --------- |
| 检测器输出的区域                | 0.54     | —        | —         |
| **GT 框 + GT 标签**（编码器上限） | **0.76** | **1.00** | **0.878** |

差距说明**瓶颈在检测、不在编码器** —— 编码器在有干净区域时几乎总能排对，  
所以优化预算应该投到检测/掩码，而不是换更大的视觉塔。

**VLM 空间问答（`scripts/12–14`）。** Qwen2-VL-2B + LoRA（4bit 量化，1359 样本，  
2 epoch / 338 step / 2954 s，显存峰值 3.684 GB，可训练 9.23M 参数占 0.42%，  
冻结视觉塔与 merger）：

| 指标       | 微调前     | 微调后                   |
| -------- | ------- | --------------------- |
| 输出格式可解析率 | 8.3%    | **100.0%**            |
| 单位正确率    | 4.2%    | **100.0%**            |
| 空间关系准确率  | 0%      | **100.0%**            |
| 距离 MAE   | —       | 0.420 m（41.7% ≤0.3 m） |
| 3D 坐标误差  | 2.756 m | **1.346 m**           |

**务必读懂这张表的边界。** 前四项是**格式与语义**能力，微调把"会不会按格式说话"  
从 8.3% 拉到 100%，这是 LoRA 最可靠的价值。但最后一行暴露了本质：  
**1.346 m 的坐标误差说明单目 RGB 恢复不出绝对尺度** —— 这不是微调不够，  
而是任务本身病态。所以本项目的架构结论是：  
**几何走投影（毫米级）、语义走 VLM（任意表达）**，而不是让 VLM 直接输出 3D 坐标。  
这个结论比"VLM 提升了多少"更有工程价值。

**加入规则引擎基线后，上述结论从经验判断变成定量证据。**  
`scripts/14_eval_vlm_spatial.py --rule-baseline` 用规则引擎在**精确 3D 地图**上回答  
同一批问题，给出几何能达到的上界。注意这是 **oracle 上界**（GT 答案本来就是这套  
规则引擎生成的，满分是预期结果）—— 它的作用是当**天花板**用于**归因**，  
而不是当"对手"：

| 任务   | 指标          | 基座          | 微调后             | **规则引擎（上界）**    |
| ---- | ----------- | ----------- | --------------- | --------------- |
| 米制距离 | 距离 MAE      | 不可解析        | 0.420 m         | **0.000 m**     |
| 米制距离 | ≤0.3m 比例    | 0%          | 41.7%           | **100%**        |
| 物体定位 | 3D 坐标误差     | 2.756 m     | 1.346 m         | **0.000 m**     |
| 相对关系 | 准确率         | 不可解析        | **100%**        | **100%**        |
| 全局   | 可解析率 / 含单位率 | 8.3% / 4.2% | **100% / 100%** | **100% / 100%** |

**读法**：微调后的 VLM 在**语义与格式维度完全追平几何上界**  
（关系准确率、可解析率、单位率都是 100%），但在**度量维度差 1~2 个数量级**。  
于是分工可以精确表述为：**VLM 负责意图解析、指代消解与结构化输出；  
米制数值必须来自几何。** 两者通过结构化输出对接（`reasoning/vlm.py` 的  
`HybridReasoner` 就是这么做的）。

⚠️ **实现这个基线时的教训**：第一版按**问题文本**匹配答案，结果一个本该满分的  
oracle 基线跑出"距离 MAE 0.178 m、坐标误差 1.001 m"。根因是**同一句话会在多个  
合成场景里重复出现而答案不同** —— 键冲突导致匹配到了别的场景的答案。  
改用 **(图像, 问题)** 做键后匹配率 100%、指标归零。  
**一个"上界"没拿到满分时，先怀疑自己的评测接线，而不是急着解释结果。**

## 五、设计取舍总结

| 决策点         | 选择                   | 理由                                                     | 代价                     |
| ----------- | -------------------- | ------------------------------------------------------ | ---------------------- |
| 物体构建        | 实例关联                 | 空间聚类会合并相邻物体                                            | 需要实例信息（可降级到聚类）         |
| 3D 表示       | 体素特征场                | 多视角融合 + 整数键 + 抗噪                                       | 内存随分辨率立方增长             |
| 开放词汇载体      | 特征向量                 | 任意文本可比                                                 | 需要 CLIP 才有文本侧          |
| **VLM 的角色** | **只做语义，不做几何**        | 单目 RGB 恢复不出绝对尺度（实测坐标误差 1.35 m）                         | 两套模块需协同                |
| **查询阈值**    | **自监督标定**（回退到编码器声明值） | 用地图自身的 (特征, 标签) 对定阈值：无需 GT、逐场景自适应、换数据集不用重扫；实测优于人工扫描的常量 | 需要地图已有 ≥2 个类别；词法路径尚未接入 |
| 推理          | 规则保底 + VLM 增强        | 保精度 + 保灵活                                              | 两套代码要维护                |
| 部署          | 快慢分级                 | 慢任务不阻塞实时链路                                             | 受 GIL 限制，非真并行          |
| 降级实现        | 每个后端都配               | CI 可跑 + 错误可二分                                          | 需要诚实标注降级代价             |

## 六、局限与后续工作

**已知局限**（详见 README"已知局限"）：

1. 离线 stub 检测器依赖 GT 框；
2. bbox 当掩码使 3D 框偏大（已量化，见 4.4；换 SAM 后误差从 1.324 m 降到 0.555 m）；
3. **多视角融合只在"水平环带"上验证过** —— 旧的虚拟相机重渲染（`virtual_camera.py`，  
   把单帧点云重渲染成 N 个视角）已**整体删除**：那只是同一份观测的重采样，不增加信息  
   （无效深度像素 42.8% → 77.0%，见 `docs/多视角数据核查报告.md`）。  
   现在的路线是 Stanford 2D-3D-S 的**真实多视角 → 一张 360° 全景**，与官方全景逐像素一致；  
   但采集装置是水平环 —— 实测 **3,345 个真实视角的光轴仰角全在 −22.9°~+23.7°**、  
   超出 ±30° 的**帧数为 0**，所以**天顶 / 天底从未被观测**，全景只是约 ±55° 的水平环带；  
   覆盖率必须报**立体角**口径（像素覆盖会低估：office_6 在 48 视角下像素 **51.6%** vs 立体角 **72.11%**，见 `runs/36_pano_dataset_stats.json`）。  
   **已产出**下游评测（§4.1：3 房间 × 24 视角，中位 0.3419 m、匹配率 0.79~0.92），  
   但它用 GT 框注入、**不是**端到端精度，也**不能**与 SUN RGB-D 单帧同口径对比  
   （数据集不同、检测来源不同）—— 见 `docs/多视角全景融合报告.md`；
4. **词法匹配不是真开放词汇** —— 且实测发现别名表在本基准上"太强"，  
   掩盖了嵌入路径的真实价值（见 4.5 的诚实边界）；
5. 异步流水线受 GIL 限制；
6. ~~ROS2 **未上真机**~~ —— 已在**两条独立路径**上跑通：  
   RoboStack Windows（里程计位姿）与 **WSL2 + Ubuntu 22.04 + ROS2 Humble  
   （`tf2_ros` 真实 TF 树）**，都是 6 帧 / 0 位姿失败 / 物体误差 0.053~0.534 m，  
   且两者**逐位一致** —— 两套独立位姿来源产出相同地图，是对 TF 约定处理的强交叉验证。  
   过程中真实 rclpy 抓出 **4 个**离线测试覆盖不到的 bug  
   （含一个根因级的：`stamp` 是 float 而 tf2 要 `Time`，异常被 identity 兜底吞掉，  
   表现为"6 帧却 0 体素、`pose_failures` 仍为 0"）。**仍未覆盖**：真机硬件联调。
7. **VLM 不能输出度量几何** —— 单目 RGB 恢复不出绝对尺度，实测 3D 坐标误差 1.35 m，  
   所以几何走投影、语义走 VLM（见"设计取舍"）；
8. **VLM 评测集偏小**，绝对数值应看作趋势而非稳定指标。

## 七、落地补充：如果机器人**只有 RGB**、拿不到深度怎么办

> 这一节回答一个很实际的质疑：本项目的输入契约是 `RGBDFrame{color, **depth_m**, intrinsics, pose}`，
> 但真实机器人上**多目 RGB 摄像头很常见、深度不一定有**（环绕相机模组、工业相机、纯视觉方案）。
> 那么这套东西是不是"实验室专用"？下面按"诊断 → 三条路 → 实测 → 建议"来答，
> **所有结论都有实测支撑**，包括一条**否定性结论**。

### 7.1 诊断：深度的依赖到底有多深

把 `src/roboground/` 全部 73 个模块按"是否读 `depth_m`"过一遍：

| 包 | 是否依赖深度 | 文件数 | 读 `depth_m` |
|---|---|---|---|
| `perception/` | ✅ 不依赖 | 16 | **0 次** |
| `mapping/` | ✅ 不依赖 | 4 | **0 次** |
| `reasoning/` | ✅ 不依赖 | 4 | **0 次** |
| `rl/` | ✅ 不依赖 | 5 | **0 次** |
| `eval/` | ✅ 不依赖 | 3 | **0 次** |
| `utils/` + 根模块 | ✅ 不依赖 | 8 | **0 次** |
| `geometry/` | ⚠️ 依赖 | 4 | 14 次 |
| `data/` | ⚠️ 依赖 | 21 | 50 次 |
| `deployment/` | ⚠️ 依赖 | 9 | 19 次 |

**结论：深度依赖**只**集中在前端**（数据层 + 几何层 + ROS2 `bridge`）。
`perception / mapping / reasoning / rl / eval / utils` 等一共 **40 个文件读 `depth_m` 的次数是 0**。

原因在数据契约的设计上 —— 层与层之间传的是 **`Observation.points_world`（世界系 3D 点）**，
**不是深度图**：

```
RGBDFrame{color, depth_m, intrinsics, pose}   ← 只有这里需要 depth_m
        │
        │ 几何层在这一步把深度"用掉"，换成 3D 点
        ▼
Observation{detection, points_world (N,3)}    ← 往上全部只认 3D 点
        │
        ▼
MapBuilder ──► SemanticMap ──► 查询 / 推理 / 输出       ← 一行都不用改
```

所以"换掉深度来源"是一处**前端组件替换**，不是全系统改造。
（这一点在 2.2 的实现映射表里对应"无模型可跑"那一列的设计哲学：
每个部件都可插拔，链路形状不变。）

### 7.2 三条补齐深度的路

| 路 | 需要什么 | 典型代价 | 适用 |
|---|---|---|---|
| **A. 真的装深度** | RGB-D 相机（RealSense/Astra）或 LiDAR | 硬件成本、标定 | 多数服务机器人**本来就有** —— 这一条被低估了 |
| **B. 多视角立体（纯几何）** | ≥2 个相机**且彼此有基线** + 已知位姿（标定 / SLAM / VIO） | 无模型、无权重；算力随视角数线性增长 | 真实**多相机机架**；本模块 `data/mvs_depth.py` 实现的就是这条 |
| **C. 单目度量深度（学习式）** | 一个深度网络（如 Metric3D / Depth Anything 系列） | 需要权重；度量精度通常远低于深度传感器 | **单目**或**共光心多目**——B 用不了时的唯一出路 |

`src/roboground/data/mvs_depth.py` 已实现 **B**（plane-sweep），并且**已验证**（见 7.3）。

### 7.3 实测：B 这条路在**什么条件下**成立

#### ★ 否定性结论：在本项目的数据集上，B **不可能**（几何原因，不是实现问题）

我原本打算直接用 2D-3D-S 的 N 个真实视角跑 plane-sweep 来演示"只有 RGB 也能出深度"，
**结果失败了**：代价函数在所有深度上**恒为常数**（z=0.5 m 与 z=8.0 m 的中位代价都是 **2.48**），
恢复出的深度毫无意义（MAE 5.4 m，而真实深度只有 0.5~3 m）。

查下去发现这不是 bug，是**几何事实**：

| 证据 | 数值 |
|---|---|
| 该采集点 46 个视角的**光心离散度** | **2.7e-06 m**（即相机间**基线 ≈ 0**）|
| 参考像素投到源相机的坐标，在深度 0.5→20 m（**40 倍**）变化下 | 只移动 **0.03 像素** |

**基线为 0 ⇒ 无视差 ⇒ 无法三角化。** 改变深度假设只是沿同一条射线前后移动三维点，
而它在另一个同光心相机里的投影方向**不变**，所以代价函数与深度无关。

> 2D-3D-S 的 `/data` 是 Matterport 式采集：**原地转一圈**拍 N 张。
> 这个性质正是本项目**全景融合**成立的前提（同一光心才能拼成一张全景），
> 但它同时也**排除了**从这份数据推导深度的可能 —— 同一个性质，一面是优点，一面是限制。
>
> 顺带记两个我自己踩的坑（都写进了测试）：
> ① 第一次以为"是 MVS 实现有 bug"，差点去改投影代码 —— 实际是几何不可能；
> ② 用合成场景验证时，手写的 `R` 让相机朝了 **−y** 而平面放在 **+y**，
>   于是"纹理"取自相机背后，测出一堆废数。改用项目里已验证的 `look_at_pose` 才对。

#### ★ 正面结论：有基线时它工作良好，且精度随基线单调改善

用**解析构造**的纹理平面（纹理是世界坐标的函数，与 `mvs_depth.py` 的投影实现完全独立）
验证实现本身，平面真实深度恒为 **3.000 m**：

| 相机基线 | 视角数 | 中位深度误差 | 估计中位 |
|---|---|---|---|
| **0.00 m** | 2 | **3.0000 m** | 6.000（完全失败）|
| 0.05 m | 2 | 0.2183 m | 3.213 |
| 0.15 m | 3 | 0.0693 m | 3.069 |
| **0.30 m** | 4 | **0.0250 m** | 3.025 |
| 0.30 m | 6 | **0.0230 m** | 3.023 |

（320×240、80 个深度平面。`tests/test_mvs_depth.py` 用较小的 160×120/48 平面锁住同一结论，
中位误差 0.069 m，阈值取 0.10 m 留余量。）

**读法**：
- 基线 **0** → 彻底失败，且是**必然**失败（不是调参能救的）；
- 基线 **5 cm**（典型双目/近距离多目）→ 20 cm 级，勉强可用；
- 基线 **15~30 cm**（典型多相机机架）→ **2.5~7 cm**，对建图足够。

> **所以对"真实多相机机器人"，B 这条路是通的**：把相机装开一点（哪怕 15 cm），
> 配合轮式里程计/SLAM 给的位姿，就能在**没有深度传感器**的情况下把 3D 链路跑起来。
> 反过来说，**共光心的相机阵列（比如一台相机转一圈、或多个镜头共用分光棱镜）
> 拿不到深度**，只能走 C。

### 7.4 建议的落地做法

1. **把深度做成可注入的前端**（本项目的架构已经支持，只需明确接口）：
   新增一个 `DepthProvider` 抽象 —— `sensor`（直接读深度）/ `mvs`（`mvs_depth.py`）/
   `mono`（调用单目度量深度模型）。三者都产出 `depth_m`，之后链路完全一致。
2. **服务机器人优先选 A**：多数配送/引导机器人本来就有 RGB-D 或 LiDAR，
   RGB-D 假设并不脱离实际；**只有在确实没有深度时才启用 B/C**。
3. **多相机机架优先选 B**：无模型、无权重、可解释，且精度与基线正相关 ——
   这是**可以靠机械设计改善**的指标（把相机间距从 5 cm 加大到 30 cm，
   实测误差从 20 cm 降到 2.5 cm）。
4. **C 是兜底**：单目/共光心场景下没有别的几何出路。但要预期**度量精度明显更差**，
   且需要额外的权重与推理预算（本项目已有"模型可插拔 + 离线降级"的机制可复用）。

### 7.5 诚实边界（这一节没做到的事）

- **RGB-only 路径尚未在真实 RGB-only 数据上端到端验证**。7.3 的正面结论来自
  **合成**纹理平面（用来验证实现正确性），否定性结论来自**真实**数据（用来证明几何限制）。
  "在真实多相机机器人上、MVS 出来的深度能否支撑到同样的定位精度" —— **还没测过**。
- **A 路（真实深度传感器）与 B/C 路的精度差距没有量化对比**。
- 本项目全部既有指标（§四）都是在**有真值深度**的数据上测的，换到 RGB-only 会**下降**，
  下降多少取决于基线、纹理丰富度与场景尺度，目前**未知**。
