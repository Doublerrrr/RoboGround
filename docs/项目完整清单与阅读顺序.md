# 第二部分 · 建议阅读顺序

## 2.1 排序原则：按**面试权重**，不按代码量

一份同岗位（普渡 VLM 算法工程师）的真实一面面经显示，16 道题的分布是：

| 方向 | 题数 | 对应项目模块 |
|---|---|---|
| **RL / 后训练** | **7** | `rl/`（1,330 行） |
| **多模态数据工程** | **4** | `data/video/` + `data/corpus/`（4,142 行） |
| LoRA / PEFT | 2 | `scripts/13` + `rl/` |
| 注意力 / 推理引擎 | 2 | 纯知识（`docs/面试答题稿_VLM与RL.md`） |
| **3D / 几何 / 机器人感知** | **0** | `geometry/` + `mapping/`（3,279 行） |

→ **`rl/` 只有 1,330 行却对应 7 道题；而项目最重的几何+地图一道题都没问到。**
所以顺序必须按权重排：**先 RL 与数据，后几何**。

> ⚠️ 但几何**不能跳过** —— 它决定你在答"你这系统怎么串起来的"时有没有底气。
> 只是它的优先级排在后面。

## 2.4 三条主线（读完应该能说出）

1. **数据决定上限**：镜头检测失效（F1 0.047）→ 修到 0.947；抽帧策略差异被去重抵消；
   金种子真值自我印证 → 指标虚高。**每个数据决策都被下游量化验证过。**
2. **能自动验证的任务，不要训 reward model**：几何规则引擎能算精确答案 →
   它就是 verifiable reward → GRPO 无需 critic、奖励不可被 hack。
3. **失败必须可归因，不能静默**：`drop_stats`、奖励分解、指标带样本量、
   诊断工具调用被测函数本身 —— 全项目贯彻这一条。

## 附二：这份清单本身是怎么保证不出错的

本文档里的**每一个数字**（测试数、文件数、行数、按包分布、逐模块行数）
都由脚本机器核对，不靠人记：

```bash
python scripts/25_audit_doc_numbers.py            # 只报告差异
python scripts/25_audit_doc_numbers.py --fix --fix-lines   # 自动修正
```

它同时是 `tests/test_doc_numbers.py` 的回归锁 —— 数字漂了会直接让 `pytest` 红，
并且报错信息里带着修法。

**为什么值得为"文档里的数字"专门做工具**：这个项目已经**三次**栽在这上面 ——
新建本文档时凭印象写模块行数（29 处全错）、加完测试后 12 处文档还写着旧数字、
后来我又手写了 5 个测试文件的行数（又错 5 处）。
三次都是同一个模式：**数字看起来精确、排版整齐，读者会默认它是量出来的。**
项目里"评估协议比代码更容易骗人"这条教训，在文档上同样成立。
